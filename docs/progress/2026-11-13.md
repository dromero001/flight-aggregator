## What was done

- **Gradle skeleton:** Gradle wrapper, Kotlin DSL, a `buildSrc` convention plugin (`flightaggregator.java-conventions`: Java 25 toolchain, `-Xlint:all -Werror`, JUnit Platform), a version catalog (`gradle/libs.versions.toml`), configuration cache and build cache on. `settings.gradle.kts` lists the remaining modules of §6 in a comment and includes only `mock-gds`. The Java 25 JDK is downloaded through the foojay resolver into `~/.gradle/jdks`. The global JDK and SDKMAN default were not touched, and Gradle was not installed globally: the distribution was downloaded to a scratch directory only to generate the wrapper.
- **`mock-gds`** (`com.flightaggregator.mockgds`), plain Java, no Spring:
  - `reference`: 32 airports (9 European hubs, 16 spokes, 7 intercontinental), each with its IANA `ZoneId` and coordinates, and 12 airlines (IB, UX, VY, BA, AF, LH, KL, TP, AZ, LX as hub carriers; FR, U2 as low-cost carriers).
  - `network`: routes derived by rule. Hubs are fully connected by their home carriers. Spokes and long-haul airports are served only from their gateway hubs, so two spokes of different hubs (e.g. SVQ→NCE) need exactly two stops. Low-cost carriers fly a fixed list of hub pairs. Block time comes from the great-circle distance.
  - `schedule`: seeded daily flights per route (flight number, local departure time between 06:00 and 22:55). Whether a flight operates on a date is a pure function of (seed, flight, date), so the legs of a day are the same whichever day the window is generated on.
  - `pricing`: `PriceModel.price(legKey, provider, instant)`, a pure function of (seed, leg, provider, 15-min bucket). It combines a distance-based fare, a per-leg fare level, a per-provider margin and a per-bucket drift (±10 %). It is also ready for the future re-price endpoint.
  - `dataset`: `DatasetGenerator.generate(Clock)` returns a `Dataset`. Each leg is sold by one, two or three providers at their own price. A configurable share of each provider's records becomes a `MalformedLeg(leg, defect)` with `Defect` ∈ {MISSING_FIELD, BAD_DATE, NEGATIVE_PRICE, UNKNOWN_AIRPORT}. The record keeps the original leg so each future serializer can render the defect in its own format; the enum fixes the exact broken values.
  - Test-only `calibration` package: an itinerary enumerator, an itinerary count and a connection census. They restate the §4 rules (dedup with the cheapest offer winning, no departed legs, same airport, MCT ≥ 45 min, layover ≤ 24 h, up to 3 legs) to estimate the itinerary count and to prove that every case is present.
- **Tests:** 67 tests (JUnit Jupiter + AssertJ), written test-first. `./gradlew build` is green, and the whole module's tests run in about 1 s.

## Decisions I made (agent's call)

- **JUnit 6.1.3 instead of "JUnit 5":** this is the latest GA release, and it is still the Jupiter programming model the design names (§6.1, §8). Spring Boot 4.1's BOM will be checked against it when Boot is added.
- **Window:** `windowDays` local dates starting on the clock's **UTC date**. Legs that departed earlier that day stay in the inventory on purpose: they are the "already departed" case, and the ingestion must filter them.
- **Determinism, more precisely:** the legs (keys and times) depend on (seed, clock date). Prices depend on (seed, leg, provider, 15-min bucket of the clock instant). Same seed + same clock bucket = identical dataset. Rolling the clock by one day keeps the legs of the overlapping days.
- **Malformed records replace the provider's valid record** instead of being added next to it. The ingestion therefore loses that offer, as it would with a real bad record. `Dataset.validLegs()` is exactly what a correct ingestion should keep.
- **Defect details:** MISSING_FIELD omits the flight number; BAD_DATE writes `2026-02-30T25:61:00+01:00` as the departure; NEGATIVE_PRICE negates the price; UNKNOWN_AIRPORT sets the destination to `ZZZ`.
- **Hub-and-spoke network written by hand** (§11 leaves the dataset contents to the builder). Only frequencies, times, operating days, sellers and prices are random.
- **Calibration lever:** to reach ~1M itineraries over 30 days, the network has to be sparse. Two-stop combinations grow with the cube of departures per airport. Defaults: 1–2 flights per route and day, each operating on 45 % of days.

## Pending (needs the user)

- **Circular itineraries:** §4 does not forbid an itinerary that visits an airport twice (e.g. MAD→LHR→MAD→JFK). They are 28 % of the estimated million. If the itinerary builder rejects them, which is what an OTA would do, the count drops to ~722k, and `operatingProbability` should be raised (to about 0.5) to recalibrate. This is a domain decision for Saturday's review of the `ItineraryBuilder`.
- **Interlining share:** 95 % of itineraries mix airlines. This follows from allowing interlining in a hub network. Worth a look during the dataset review, in case a higher single-carrier share is wanted for the Carrier-filter demo.
- **Process note:** the code-quality review ran once over the whole module after the feature commits rather than before each commit. Its findings are fixed in commit `Tidy the generator after a code-quality review`.
